## F1 开发位置（已定）

- **决定：** 在 ly-island 仓库的孤立分支 `framework` 上开发。
  - 这个分支和 `main` 没有共同历史，不合并进 `main`；
  - 测试站点是 dev.rqly.com；
  - 成熟后把分支推成新仓库的 `main`，步骤见[路线](roadmap.md#拆成独立仓库的步骤)；
  - rqly.com 暂时不动。
- **理由：** 孤立分支的历史里只有框架本身，拆分时不会带出 rqly.com 的内容和历史，也不会误发布到线上。`scripts/release.py` 只发布 `main` 上的标签。
- **来源：** 站主，2026-10-13。

## F2 项目名称（待定）

- **现状：** 先用暂名"群岛框架"，英文仓库名在拆分前确定。
- **要求：** 短，好记，和"岛"或"云海"有关，在 GitHub 和 npm 上没有被占用。

## F3 许可证（已定）

- **决定：** MIT，与 ly-island 相同。
- **理由：** 用户会复制模板、修改主题和规则，宽松的许可证最省事。

## F4 部署目标（已定）

- **决定：** 第一目标是 Cloudflare 免费档：Workers 静态资源、Worker、D1、定时任务，加上一键部署按钮。
- **同时保持可迁移：**
  - 岛务 Worker 用 Hono 编写；
  - 数据库有 D1 和 SQLite 两种适配层；
  - CI 同时测试两种。
- **详见：** [部署](deployment.md)。

## F5 内容来源（已定）

- **决定：** 文章是用户仓库里的标准 Markdown；D1 只存互动数据。想在浏览器里写，就接现成的 Git 编辑器，不自己写。
- **理由：**
  - 免费档下最省资源；
  - 内容天然可以迁移；
  - "AI 起草、人确认"可以直接用 PR 和合并来实现。
- **注意：** rqly.com 现在是浏览器后台写作。这条只针对新框架，rqly.com 的迁移以后单独决定。

## F6 身份（已定）

- **决定：** 岛的身份 = HTTPS origin + Ed25519 密钥。
  - 首次信任，接收方保存每座岛的密钥历史；
  - 换钥用接收方已信任的旧钥验证，沿密钥日志成链；
  - 搬家需要新旧两边都确认，确认后记下迁移关系。
- **详见：** [协议](protocol-v0.md#身份)。

## F7 不上链（已定）

- **借鉴：** 自有身份、签名记录、可替换的中继（AT Protocol、Nostr），收件箱和动态模型（ActivityPub），自有域名和 Webmention（IndieWeb）。
- **不做：** 区块链、代币、NFT、钱包。
- **理由：** 这些会带来成本、门槛和投机，对"坚持记录"没有帮助。

## F8 不审核（已定）

- **决定：** 没有平台审核。签名、接收策略、屏蔽、限速、人机验证都是岛主自己的工具。
- **收件箱分级（2026-10-14，来自评审）：** 签名只能证明来源，不能证明内容不是垃圾，所以：
  - 邻居和白名单进收件箱；
  - 朋友的朋友只进摘要；
  - 陌生人进"陌生来信"，不发即时通知；
  - 限速按可注册域名合并，新岛减半；
  - 不采用工作量证明（PoW），理由见[协议](protocol-v0.md#未决问题)。
- **来源：** 站主。
- **详见：** [协议](protocol-v0.md#签名不等于可信按关系分级)。

## F9 主题与世界观（已定）

- **决定：**
  - 保留浮空岛，作为"云海群岛"的世界观和旗舰 3D 主题，点击后才加载；
  - 默认主题是轻量的 2.5D 等距岛；
  - 纯文字主题必备；
  - 协议里不出现"岛"的外形，其他形态（小屋、星球）都可以做成主题。
- **理由：**
  - 拜访、灯塔、漂流瓶这些社交动作需要一个共同的世界，没有它就只是又一个博客框架；
  - 免费托管不限制主题，3D 在访客的设备上渲染；
  - 真正的约束是首屏大小和低端设备。
- **详见：** [扩展接口](extensions.md#主题)。

## F10 成长规则（已定）

- **决定：**
  - 规则写在开源代码里，谁都可以改（站主原话）；
  - 只看自己的记录：别人的拜访和浇水只带来装饰效果，不加分；
  - 按周算连续，不按天；
  - 不惩罚，已解锁的外观不收回。过去的解锁作为显式输入，存在仓库的解锁台账里；
  - 没有全局排行；
  - 默认分值沿用 rqly.com。
- **详见：** [扩展接口](extensions.md#成长规则)。

## F11 AI 管家（已定）

- **决定：**
  - AI 可以读、整理、提醒、起草；发布和对外的社交动作必须由人确认；
  - 自带模型，不跑在 Worker 里；
  - 提供 MCP 服务；
  - 给 AI 的令牌只有"读"和"起草"权限。
- **详见：** [扩展接口](extensions.md#ai-管家)。

## F12 通知（已定）

- **决定：**
  - 固定的本地事件格式；
  - 渠道可以替换，先做 Telegram、ntfy、通用 webhook；
  - 邮件在核实 Cloudflare 免费档的发送条件后再做；
  - 留言、瓶子被捡即时通知，其余默认汇总成摘要；
  - 记录提醒默认关闭。
- **详见：** [扩展接口](extensions.md#通知)。

## F13 静态生成器（待定）

**倾向 Astro：**

- 成熟；
- 默认输出不带 JavaScript 的静态页面；
- 内置 Markdown 和内容集合，适合做主题；
- 官方支持部署到 Cloudflare。

**需要知道：** Astro 在 2026 年 1 月被 Cloudflare 收购，官方表示会继续开源，并继续支持部署到多个平台。它的产物是普通静态文件，换平台不受影响。

**备选 Eleventy：** 更轻，依赖更少，但做组件化的主题不如 Astro 方便。

**计划：** 第 1 阶段的第 2 个 PR 用同一个最小示例对比两者的构建产物大小、依赖数量和主题写法，再定。

## F14 协议版本（已定）

- **决定：** `islands/0` 阶段允许不兼容的修改，每次都记进协议文档的修改记录。进入 `islands/1` 后，同一个大版本内只能新增。
- **理由：** 现在没有外部实现，过早冻结会把早期的错误固定下来。
