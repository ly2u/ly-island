## A. 已实测的缺陷

### A1. `/api/posts`、`/api/search`、`/api/admin/search` 耗时平方增长

- **位置：** `apps/rqly-sites/server.mjs:76`（`publicOrganizedRecord`）、`:232`、`:233`、`:178`
- **原因：** `publicOrganizedRecord(post)` 每次调用都执行 `publishedPosts()`，它会重新读取并解析整个 `posts.json`。接口对每篇文章调用一次，所以 N 篇文章会解析 N+1 次（实测 100 篇文章解析 101 次）。管理端搜索在 `map` 里重复调用 `readPosts()` 和 `organizationStore.read()`，同类问题。
- **触发：** 岛屿每次打开都会调用 `/api/posts`（`apps/ly-island-preview/src/main.js:110` 调用 `loadPublicPosts`，请求在 `:107`，超时 8 秒）。不需要登录，访客就能触发。
- **预期：** 一次请求只读取一次。
- **实际：**

| 文章数 | 修复前 `/api/posts` | 修复后 |
|---|---|---|
| 30 | 88 ms | 未测 |
| 150 | 1,729 ms | 23 ms |
| 600 | 28,280 ms | 56 ms |

  `/api/search` 和管理端搜索的数值几乎相同。文章增加 4 倍，耗时增加约 16 倍。
- **影响：** 读盘和解析都是同步的，单线程，所以一个慢请求会让其他所有访客的请求排队。按这组数据外推（假设保持平方增长，属估计），约 300 多篇文章时请求会超过前端的 8 秒超时，首页读不到文章列表。文章正文更长时更早。
- **修复：** 本 PR 第 2 个提交，让调用方一次性算好 `published` 和 `catalog` 再传入。响应结构不变。
- **复现：** `docs/reviews/2026-10-07-repro/bench-list-endpoints.mjs`。最小测试：`scripts/check-scale.mjs`，按"读取次数"断言而不是计时，所以在 CI 里稳定。它在原代码上失败（`parsed posts.json 81 times for 80 posts`）。

### A2. `/api/admin/media` 对每张图片重读全部历史文件

- **位置：** `server.mjs:68`（`mediaReferences`）、`:182`
- **原因：** 每张图片调用一次 `contentHistory.references()`，它会读取并校验（含 SHA-256）全部历史版本文件。
- **实际：**

| 文章 / 图片 / 每篇历史版本 | 修复前 | 修复后 |
|---|---|---|
| 30 / 60 / 3 | 377 ms | 20 ms |
| 100 / 300 / 5 | 10,192 ms | 100 ms |
| 250 / 800 / 8 | 在 280 秒测试时限内未完成 | 668 ms |

- **影响：** 站主打开图片库时整个站点卡住。图片上限是 2000 张，历史上限是每篇 30 个版本，这个上限范围内问题会更严重。
- **修复：** 本 PR 第 2 个提交，历史只读一次。图片库的 668 ms 里剩余的成本是对每张图片扫描所有正文，将来可以改成"一次扫描建索引"，这里没有做，因为改动更大。
- **复现：** `docs/reviews/2026-10-07-repro/bench-media-library.mjs`；`check-scale.mjs` 里有对应断言，在原代码上读取了 100 次（20 张图 × 5 个历史文件）。

### A3. 白名单静态文件读不到时，进程会退出

- **位置：** `server.mjs:239`（静态资源）、`:134`（`/media`）。两处都是 `fs.createReadStream(...).pipe(res)`，没有 `error` 监听。
- **触发：** 白名单里的文件在请求时不存在或不可读，比如发布时复制不完整、权限错误。
- **预期：** 返回 404 或 500，服务继续运行。
- **实际：** 抛出 `Unhandled 'error' event`，Node 进程退出。已复现（`docs/reviews/2026-10-07-repro/crash-missing-static.mjs`）。
- **为什么说是根因没修：** REVIEW.md 末尾记录的那次修复只删除了一个不存在的白名单项，`check-static-resilience.mjs` 也只测试"不在白名单里的名字"，所以同一类崩溃仍然可能。
- **缓解：** `compose.yaml` 里有 `restart: unless-stopped` 和健康检查，所以会自动重启，影响是短暂中断。
- **修复：** 本 PR 第 1 个提交：加 `pipeFile()` 处理流错误；缺失文件返回 404。测试已加入 `check-static-resilience.mjs`，在原代码上会触发同一个崩溃。

## B. 宏观维护风险（建议，未改代码）

### B1. 代码密度极高

- `server.mjs` 只有 246 行，却有 44 KB，最长一行 1,098 个字符；`admin.js` 295 行、64 KB、最长一行 2,917 个字符。`server.mjs` 的 `handler`（第 128 到 244 行）是一个 22 KB 的串联 `if`；全文约有 60 处路由判断，绝大多数都在这个函数里。
- 后果是直观的：上面 A1 到 A3 的修复只改了 `server.mjs` 的 17 行，diff 却有 7.6 KB（平均每行 449 个字符）。评审者很难看出具体改了哪里，合并冲突的概率也更高。
- **建议顺序：**
  1. 先单独做一个纯格式化提交（Prettier），不改任何行为，用现有 10 个可运行的检查脚本做保险。
  2. 再加 ESLint（至少 `no-unused-vars`、`no-floating-promises` 这类规则）。
  3. 最后再把 `server.mjs` 按职责拆开，例如 Markdown 渲染、模板渲染、公开路由、管理路由、AI 路由、HTTP 工具函数。
- **注意：** 第 3 步会让 B2 中的备份脚本失败，所以先处理 B2。

### B2. `backup.sh` 把源码文件逐个写进 `tar` 命令

- **位置：** `scripts/backup.sh:53` 到 `:72`，逐个列出了 `server.mjs`、各 store、各个 check 脚本等。
- **后果：**
  - 文件改名或拆分后，`tar` 会因为路径不存在而失败（我验证过：任何一个路径缺失，`tar` 都以退出码 2 结束），`set -e` 使脚本退出，当天没有备份（服务会被 `recover` 恢复，但没有产物）。
  - 新增的顶层 `.mjs` 模块或检查脚本不在列表里，不会被备份，而且没有任何提示（例如本 PR 新增的 `check-scale.mjs`）。`public/` 和岛屿目录是整目录备份的，不受影响。
  - 源码已经在 Git 里，这部分备份只是重复；真正需要的是数据、配置和密钥。
- **建议：** 只备份数据和配置（`/srv/ly-data/sites`、Caddy 状态、`env/`、`.env`、Codex 凭据、compose 文件），源码靠 Git。这样重构不再影响备份。
- **相关：**
  - 备份只放在同一台 VPS 上（README 说明是站主的决定），数据和密钥在同一个未加密的归档里。如果以后加异地副本，需要先加密（例如 restic 或 rclone crypt）。
  - 定时器是每天 UTC 03:15（北京时间 11:15），备份期间会停掉 `sites` 和 `caddy`，网站有短暂不可用。可以改到你所在时区的深夜，或只停会写数据的 `sites`。

### B3. 仓库不是部署来源，发布靠手工复制

- 文档写明生产从 `/opt/ly-stack/apps/` 运行，仓库工作树是独立的，"Git 拉取或合并不会自动替换生产服务"（README.md、docs/DEPLOYMENT.md）。
- `scripts/deploy-host.sh` 写死了历史镜像标签（第 32、45 行的 `ly-sites:initial-20261005-civilflow-link`），而且只运行 `check.mjs`（第 24 行），没有运行另外 11 个检查脚本；DEPLOYMENT.md 又说它不能代替当前发布步骤。
- 后果：当前的发布流程只存在于文档的 6 个手工步骤里，每次发布都要手动复制源码，仓库和线上容易漂移。
- **建议：** 写一个 `scripts/release.sh`，按 DEPLOYMENT.md 的 6 步实现：检出指定标签、运行全部检查、用提交哈希给镜像打标签、`compose up`、等待健康检查、失败自动回滚到上一个标签。注意 CONTRIBUTING.md 要求改动部署流程前先讨论，所以我没有直接写。

### B4. 早期双站包遗留，文档与现状矛盾

- `apps/rqly-sites/` 里仍有早期的 `Caddyfile`、`Dockerfile`、`compose.yaml`、`compose.panel.yaml`、`README.md`、`VALIDATION.md`。
- 该 README 第 145 行写"没有 npm 依赖，无需执行 npm install"，第 3 行写"运行不依赖第三方 npm 包"，但 `package.json` 依赖 `sharp`；README 写 Node 22，根 README 和 CI 写 Node 24，`engines` 是 `>=22`。
- `/api/review`（`server.mjs:154` 起）有三条路径：规则检查、Codex 桥接、OpenAI 兼容接口加访问码。根目录 `compose.yaml` 没有配置后者所需的 `AI_API_KEY` 和 `REVIEW_ACCESS_TOKEN`（`env/sites.env` 我看不到，所以只能说"很可能没用到"），但它仍在维护和测试。
- **建议：** 把早期包移到 `legacy/` 或删除；确认第三条 AI 路径是否还需要，不需要就删掉。

### B5. 存储层：重复实现，没有读缓存

- JSON 的原子写（临时文件加 `rename`）在 9 个文件里各写了一份（`flag:'wx'` 出现在 10 个文件里，其中 `media-store.mjs` 写的是图片，不算同一种）。
- 每次读取都完整解析并校验整个 JSON（例如 `editor-drafts.read()` 每次校验全部草稿）。
- **建议：**
  1. 抽出一个 `lib/json-file.mjs`（原子写、带 `schemaVersion` 的读取）。
  2. 之后可以加进程内读缓存，因为是单进程且写入是同步的。注意：现有调用方会原地修改 `readPosts()` 返回的数组（例如 `.sort()`、`posts[index]=`，见 `server.mjs:181`、`:219`），缓存必须返回副本，否则历史快照会被污染。
  3. 文章超过几百篇、需要多进程，或者信箱接近 5000 条（目前整个信箱是一个 JSON）时，再评估换成 SQLite。CONTRIBUTING.md 已说明数据库迁移需要单独讨论，所以这里只给出时间点。

### B6. 岛屿前端自己重算成长数据

- `main.js:32` 用全部文章重新计算积分，服务端 `island-store.mjs:7` 的 `growthStats` 是同一个公式，而 `/api/island`（`server.mjs:234`）已经返回了 `stats`。两份实现，改一份忘了另一份就会显示不一致。
- 另外 `/api/posts` 没有分页，岛屿一次取全部文章。到了几百篇需要分页或只取最近若干条。
- **建议：** 前端直接用服务端的 `stats`。

### B7. 静态资源缓存

- JS 和 CSS 的 `Cache-Control` 是 `public,max-age=3600`（`server.mjs:239`），文件名没有哈希，HTML 却是 `no-cache`。发布新版后，用户最长一小时内可能拿到旧脚本加新接口。目前靠手工加 `?v=platform-v1` 之类的参数。
- `/media/*` 用 `no-store`（`:133`），每次查看都重新下载，并且每个图片请求都会扫描一遍全部文章。如果出于隐私（撤回图片）选择了 `no-store`，可以改成 `no-cache` 加 `ETag`，仍然每次校验，但不必重复下载。

## C. 做得好的地方

- 认证与会话：scrypt 加 `timingSafeEqual`、`HttpOnly` 和 `SameSite=Strict` 的 Cookie、CSRF 令牌、自定义请求头、`Origin` 与 `Sec-Fetch-Site` 检查、`If-Match` 版本冲突。
- 前端：访客留言全部用 `textContent` 渲染；`innerHTML` 只用于服务端已转义的 Markdown 结果和静态模板；CSP 是 `script-src 'self'`。我用 14 个常见攻击载荷测了 Markdown 渲染器，没有发现可执行输出（这只是抽样，不是证明）。
- Caddy 对所有反代都写了 `header_up X-Real-IP {remote_host}`，所以限流用的 IP 不能被客户端伪造。如果以后在前面加 Cloudflare，需要同时配置可信代理，否则所有访客会共用同一个 IP 桶。
- AI：工具白名单、写入动作需要站主确认并绑定会话和文章版本、桥接服务是只读沙箱并且从不授予审批、systemd 单元做了加固。
- 数据：所有写入先写临时文件再 `rename`；JSON 损坏时报错而不是静默清空；各类上限都写明了。
