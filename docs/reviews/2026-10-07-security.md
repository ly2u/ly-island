# 安全审查（基于 main `3b72c47`，2026-10-07）

范围：认证与后台、信任边界、隐私数据、传输安全、域名防冒用、依赖与供应链、公开仓库的信息暴露。

方法：读代码和配置，扫描 Git 历史，查询公开 DNS 记录。

不在范围内：CivilFlow（站主决定暂不考虑）、渗透测试、VPS 主机本身的加固。

**无法核实的项：**

- 线上实际返回的 HTTP 头：审查环境无法访问 rqly.com；
- rqly.com 是否经过 Cloudflare 代理；
- rqly.com 的 MX 记录：查询被限流；
- VPS 的 SSH 和系统更新配置。

这些项在下文中标为"需核对"。

## 做对了的地方

先列出来，后续改动不要破坏这些：

- **会话：** 令牌只存哈希；Cookie 带 `HttpOnly` 和 `SameSite=Strict`；CSRF 令牌加自定义请求头加 `Origin`/`Sec-Fetch-Site` 校验；修改密码会撤销全部会话。
- **密码：** 使用 scrypt，按 IP 限制失败次数。`X-Real-IP` 由 Caddy 覆盖设置，客户端无法伪造。
- **AI：** 写入需要站主确认；工具有白名单；桥接只读沙箱，从不授予审批。
- **公开内容：** 只投影已发布记录，草稿不泄露；图片只在被已发布正文引用时公开；Markdown 渲染时转义并限制链接协议。
- **容器：** `sites` 只读文件系统、`no-new-privileges`、非 root 用户、内存上限。
- **Git 历史：** 扫描了常见密钥格式（API key、私钥、bcrypt/scrypt 哈希、GitHub token），没有发现泄露。

### S1. 后台只有一个密码，且与公开入口、AI 能力在同一进程（高）

**依据：**

- 同一个 Node 进程同时处理三类请求：
  - 任何人可调用的写入接口：信箱投递 `apps/rqly-sites/server.mjs:150`，七嘴审阅 `:155`；
  - 登录 `:169`；
  - 全部后台接口 `:172` 起，以及 AI 对话和站点工具 `:144`。
- `compose.yaml:26` 把 AI 桥接的 socket 挂进了这个容器。通过它可以使用站主的 Codex 订阅，并通过站点工具写入草稿。
- 后台认证只有一个密码（`apps/rqly-sites/admin-auth.mjs:20` 起），会话有效 7 天。

**风险：** 公开入口里只要有一个漏洞，或者密码泄露，攻击者就能同时拿到内容写入权和 AI 能力。仓库是公开的，攻击者可以仔细研究全部代码，寻找漏洞的成本很低。

**建议：** 见决策 0006。第一步是给后台和 AI 相关路由加第二道门，第二步是拆分进程。

**验收：** 没有第二个因素就无法到达后台登录之后的任何接口；公开容器内没有 AI socket。

### S2. 域名可被冒用发信（中）

**依据**（2026-10-07 通过公开 DNS 查询）：

| 域名 | SPF | DMARC |
|---|---|---|
| `7zui.com` | 无 | 无 |
| `rqly.com` | `v=spf1 include:_spf.mx.cloudflare.net ~all`（软失败） | 无（`_dmarc.rqly.com` 无记录） |

**风险：** 任何人都可以伪造 `xxx@7zui.com` 或 `xxx@rqly.com` 发件人发邮件，很多收件方会照常投递。这可以被用来冒充站主钓鱼。

**建议：** 只需修改 DNS，几分钟就能完成。

- **`7zui.com`**（不收发邮件）：
  - SPF：`v=spf1 -all`
  - `_dmarc` TXT：`v=DMARC1; p=reject`
- **`rqly.com`**（通过 Cloudflare 邮件路由收信）：
  - 增加 `_dmarc` TXT，先用 `v=DMARC1; p=none; rua=mailto:<你的邮箱>` 观察两周；
  - 确认没有合法的外发邮件被误伤后，改为 `p=reject`；
  - 如果从来不用 `@rqly.com` 发信，SPF 可以收紧为 `-all`。

**验收：** 两个域名都有 DMARC 记录，最终策略为 `reject`。

### S3. 没有 HSTS（中）

**依据：** `Caddyfile` 的所有站点块里都没有 `Strict-Transport-Security`。Caddy 会把 HTTP 自动跳转到 HTTPS，但首次访问和降级攻击仍有窗口期。

如果 Cloudflare 那边已经开启了 HSTS，这一条已被覆盖（需核对）。

**建议：**

- 在 `rqly.com`、`7zui.com`、`midas.rqly.com` 的站点块里加上 `Strict-Transport-Security`；
- 先用较短的 `max-age` 观察，确认所有子域名都走 HTTPS 后再加长；
- 是否加入浏览器预载列表，由站主决定。

**验收：** 三个域名的 HTTPS 响应都带 HSTS 头。

### S4. 如果经过 Cloudflare 代理，按 IP 的限制会失效或误伤（中，需核对）

**依据：**

- 域名的 DNS 在 Cloudflare 上；`apps/rqly-sites/README.md:56` 起的说明里也提到可以开启代理。
- Caddy 用 `header_up X-Real-IP {remote_host}`（`Caddyfile:26`、`:37`、`:49`）把连接方的 IP 传给 Node，Node 在 `server.mjs:92` 以它作为访客 IP。
- 如果开启了代理（橙色云），连接方就是 Cloudflare 的节点，而不是访客。

**风险：** 以下限制都按这个"访客 IP"计算：

- 登录失败锁定：每个 IP 失败 10 次锁 15 分钟；
- 信箱限流：每个 IP 每小时 5 次；
- AI 每 IP 每小时的额度。

开启代理后，它们会失效（攻击者分散到不同节点），或者误伤（某个节点上的一个攻击者让同一节点后的所有人都被锁住，包括站主）。

**建议：**

1. 先在 Cloudflare 控制台核对这三个域名是"仅 DNS"还是"已代理"。
2. 如果是已代理：在 Caddy 中把 Cloudflare 的地址段配置为可信代理，并从 Cloudflare 提供的客户端 IP 头取真实 IP。
3. 或者改回"仅 DNS"。

**验收：** 后台记录的访客 IP 是真实访客地址。

### S5. 依赖与基础镜像没有安全更新提醒（中）

**依据：**

- 仓库里没有 `.github/dependabot.yml`；
- 基础镜像使用浮动标签：`apps/rqly-sites/Dockerfile:1` 的 `node:24-alpine`、`compose.yaml:61` 的 `caddy:2-alpine`、`scripts/release.py:44`；
- GitHub Actions 按版本标签引用（`.github/workflows/check.yml`）；
- VPS 是否开启了自动安全更新，需核对。

**风险：** `sharp`、`three`、`vite`、Node、Caddy 出现安全公告时没有任何提醒。浮动标签还会让同一个 Git 标签在不同时间构建出不同的镜像。

**建议：**

- 开启 Dependabot 的安全提醒和版本更新：两个 npm 目录、GitHub Actions、Dockerfile；
- 基础镜像固定到摘要，由 Dependabot 提 PR 升级，走正常的发布流程；
- 在 VPS 上确认 Debian 的 `unattended-upgrades` 已开启；
- 在仓库设置里开启 GitHub 的 secret scanning 推送保护（公开仓库免费），防止以后误提交凭据。

**验收：** 依赖有更新时能自动收到 PR；镜像摘要记录在发布记录中。

### S6. 公开仓库详细暴露了服务器布局（低）

**依据：** README、`docs/`、`scripts/`、`systemd/` 写明了：

- 所有路径：数据、备份、socket、凭据目录；
- 服务名、后台地址、端口布局；
- 运维流程。

**风险：** 这些本身不是漏洞，但会大幅降低攻击者摸清系统的成本。这也意味着系统的安全不能依赖"别人不知道"，这一点强化了 S1 的优先级。

**建议：** 不必隐藏这些文档，它们对维护有价值。重点是确保每一层都假设攻击者已经读过全部文档：S1 的第二道门、S3、S5。

### S7. CSP 允许内联样式（低）

**依据：** `server.mjs` 和 `Caddyfile:19` 的 CSP 都包含 `style-src 'self' 'unsafe-inline'`；`script-src` 只有 `'self'`，这一点做得好。

**风险：** 有限。在已经存在 HTML 注入的前提下，内联样式可被用于界面伪装或数据外泄。

**建议：** 前端重构时逐步去掉内联样式，然后删掉 `'unsafe-inline'`。不需要专门为此改动。

## 隐私与其他

### P1. 访客数据缺少保存期限和删除说明；限流记录使用未加盐的 IP 哈希（中）

**依据：**

- 信箱保存私信正文和选填的回信邮箱；页面说明了"仅岛主可见"，但没有说明保存多久、如何要求删除。
- `apps/rqly-sites/mailbox-store.mjs:17` 用 `sha256(IP)` 作为限流键，并写入 `mailbox.json`。只保留最近一小时，但会进入每日备份。IPv4 地址只有约 43 亿个，这个哈希可以穷举还原，实际上等于保存了 IP。
- 服务器托管在德国，访客可能来自欧盟。

**建议：**

- 限流键改为带服务器密钥的哈希（HMAC），密钥定期轮换；
- 定一个信件保留期限，例如归档一年后删除；
- 在信箱页加一段简短的隐私说明：保存什么、多久、怎样要求删除。

这不是法律意见，是否需要更正式的隐私政策，请站主自行判断。

### P2. 信箱容量可被耗尽（低）

**依据：** `mailbox-store.mjs:21` 到 `:23` 规定：每个 IP 每小时 5 次，全站每天 100 次，总量上限 5000 条。

**风险：** 一个人换几个 IP，就能用完当天的 100 次额度，让真实访客当天无法投递。长期下去还会触到 5000 条的总上限，之后信箱不再接收。

**建议：** 已归档的信件不计入 5000 条上限，或按 P1 的保留期限清理；每日额度用完时在后台显示提醒。

### P3. Codex 订阅以服务方式调用（视条款，需站主核对）

**依据：** `apps/personal-ai/README.md` 和 `bridge.py` 用个人订阅登录，在服务器上以常驻服务的形式调用 Codex。

**风险：** 是否符合订阅条款需要站主自己核对。如果条款只允许个人通过官方客户端使用，账号可能被限制。此外，凭据 `auth.json` 包含在未加密的每日备份中，备份一旦泄露，这个账号也会被接管。

**建议：** 核对条款；备份加密见决策 [0010](../decisions/0010-backup-and-monitoring.md)。
